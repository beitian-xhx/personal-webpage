最近做了一个计算机视觉方向的练习项目：实时识别游戏画面中的人物，并实现"跟拍锁定"功能。把完整过程记录如下，包括思路、踩过的坑和用到的工具。

## 一、屏幕捕获

第一步是把游戏窗口的画面实时抓下来，交给模型检测。抓屏没有依赖 mss、dxcam 这类第三方库，直接用 ctypes 调用 Win32 的 BitBlt。抓屏放在一个后台线程里持续执行，主循环只取最新一帧，这样抓屏与推理并行，帧率由较慢的一方决定。窗口移动或缩放时，每帧重新获取客户区坐标，画面不会偏移。

这里遇到第一个坑：屏幕分辨率对不上。系统返回 1707×1067，而实际分辨率是 2560×1600，抓出来的画面整体错位。原因是进程没有开启 DPI 感知，Win32 API 返回的是逻辑像素。调用 SetProcessDPIAware() 后问题解决，这个细节排查花了些时间。

## 二、数据集与微调（失败记录）

最初的思路是训练一个针对游戏角色的专用模型，流程比较标准：

1. 录制游戏视频，写脚本按固定间隔抽帧（每秒一帧）；
2. 用 labelImg 手工标注人物框；
3. 编写脚本把标注结果整理成 YOLO 格式，按时间顺序划分训练集与验证集（80/20），未标注的帧作为背景样本放入训练集；
4. 基于 YOLO26n 微调，训练 43 个 epoch，在第 23 轮触发早停。

结果并不理想：mAP50 约 0.5，召回率 0.27。小样本微调带来了明显的灾难性遗忘，模型对"人"这一通用类别的识别能力反而下降。

结论是放弃微调，改用原始 yolo26n（COCO 预训练权重），检测时只保留 person 类（classes=[0]）。数据量不足时，通用预训练模型是更可靠的选择，这条经验后来也记录了下来。

## 三、吸附与跟拍

检测稳定后，开始实现"视角吸附"：当屏幕中心靠近某个人物时，视角平滑地吸附过去并跟随目标移动，用于录屏、直播等需要跟拍的场景。

实现逻辑分为几步：

1. 目标点：取人物框水平中心，垂直位置通过参数 aim_y 调节（0 为头顶，0.3 为胸口，默认 0.3）；
2. 目标选择：屏幕中心进入吸附半径后，选择距离最近的人物锁定；锁定后优先延续上一帧目标，目标丢失则自动重新锁定最近目标；
3. 平滑输出：吸附点先做一次 EMA 平滑，抑制检测框的帧间抖动；移动量再做一次 EMA 平滑控制跟手程度；单帧移动量限幅防止视角跳变；两次移动之间加入约 0.1s 的冷却，减少高频微移。

最初直接按检测结果移动视角，画面抖动非常明显。经过多次调整，最终采用"目标点平滑 + 移动平滑 + 限幅 + 冷却"的组合才达到稳定效果。

## 四、控制面板

吸附强度、灵敏度、半径、吸附点位置、平滑系数、冷却时间等参数，运行时才知道是否合适。为此加入了一个 Tkinter 置顶控制面板：参数用滑动条实时调节，总开关用复选框控制（关闭后视角完全自由），状态栏实时显示帧率、检测人数和目标距离。

面板置顶且不抢焦点，配合游戏的无边框窗口模式可以一直悬浮显示。另外，原来用 ESC 退出与游戏按键冲突，改为关闭面板窗口即退出。

## 五、整体流程

\`屏幕/游戏窗口 → BitBlt 抓屏（后台线程）→ YOLO person 检测 → 吸附点定位 → 目标选择（半径 + 最近 + 上一帧延续）→ 平滑处理 → 视角吸附输出\`

运行环境：RTX 5060 Laptop（8GB 显存）、ultralytics 8.4.116、torch 2.11.0+cu128。输入尺寸 1280 时单帧推理约 46ms，远距离小目标的检测效果比 640 明显更好。

## 小结

项目目前包含两个入口：main.py（检测并绘制边框）和 head_track.py（检测 + 吸附 + 控制面板）。实现仅依赖 ctypes、OpenCV 与 Ultralytics，没有使用额外的屏幕捕获库。代码已开源在 github.com/beitian-xhx/obs-character-snap-demo。

回顾整个开发过程，最有价值的是那次微调失败——它让我更清楚地理解了小样本下微调的局限，也直接决定了后续的技术选型。





# V1优化版

在把人物吸附 Demo 放进实际对局画面后，依次解决了镜头慢半拍、人物静止却绕圈、检测点抖动等问题。记录从根因分析到 TensorRT 加速的完整优化过程。

额外使用TensorRt进行优化

上一篇记录了人物吸附 Demo 从抓屏到跟拍锁定的过程。这次是把同一套逻辑放进真实对局画面里跑，遇到的问题比 demo 阶段具体得多：镜头总是慢半拍、人物站着不动镜头却在绕圈、吸附点随人物姿态抖个不停。这些都不是"再调调参数"就能解决的，得回头抠代码和原理。把这段优化过程记下来，重点是几个真正管用的改动。

## 一、三个问题，两个根因

实战反馈的问题有三个：吸附延迟过高，镜头跟不上移动的目标；人物静止时相机反而持续绕圈；检测点随人物姿态变化抖动明显。另外追加了需求：远处的目标（框面积约等于屏幕 5%）要能稳定识别，贴着镜头的近景大人物（框高超过屏幕 60%）不要吸附。

先排查延迟和绕圈，找到两个根因。

### 根因一：声称的"速度外推"一直是死代码

原代码里有一个速度外推，用来补偿抓屏和推理造成的延迟。但它有 bug：位置历史记录的是推理完成时刻的时间戳，外推计算用的却是同一个循环时刻。

```plain
locked_history.append((now, hx2, hy2))   # now = 推理完成时刻
...
t1 = locked_history[-1][0]
delay = now - t1                          # now 与 t1 是同一个值
pred_hx = x1 + vx * delay                 # delay 恒为 0，外推从未执行
```

结果预测点永远等于当前检测点，而检测点描述的是一帧约 30-50 毫秒前（BitBlt 抓屏约 20 毫秒 + 推理约 30 毫秒）的画面。延迟补偿实际上从没生效过，这是"镜头慢半拍"的直接原因。

### 根因二：没有死区的正反馈环导致绕圈

吸附点取在人物框顶部往下 30% 处，而 person 检测框最抖的边恰恰是顶部——姿态、发型甚至遮挡都会移动框顶。960 推理尺寸放大回 2560 屏幕后，框顶抖动约有正负 5-8 像素。

代码没有任何死区：检测点抖 1 像素就发一次完整鼠标移动，相机跟着转，下一帧检测位置又跟着变——相机在追自己的影子。这个反馈环带着约两帧的管线延迟，在增益为 1.0 时处于临界甚至发散状态，所以静止人物也会一直绕圈。

### 第一次修复与自检

对应做了几件事：抓屏位置记录真实抓屏时刻，外推从"抓屏时刻"算到当前时刻；加了中心死区（默认 8 像素），目标基本居中就不动；速度做 EMA 低通再限幅；把吸附逻辑抽成纯函数 `aim_step()`，并写了一个闭环仿真自检来验证防绕圈效果。

自检里的对照很直观：同样的静止目标加抖动参数，新逻辑相机最大偏移 0 像素；旧逻辑对照则是持续发散——模型把绕圈问题复现出来了。匀速目标在真实增益下最大滞后只有 28 像素。

## 二、砍延迟：先测，再改

顺着延迟往下查，先用基准脚本量了各环节耗时，瓶颈一目了然。

```plain
BitBlt 全屏抓屏（2560x1600）：中位 52ms   ← 最大瓶颈
推理 (608,960)：约 22-40ms（受笔记本功耗波动影响）
推理 (640,640)：约 26-32ms
```

抓屏占了将近一半的预算，而且注释里写的"约 20ms"和实测 52ms 差很远。换用 DXGI 抓屏（dxcam）后降到平均 3.65 毫秒，约 14 倍提速，抓屏从最大瓶颈变成最不是瓶颈的部分。

接着把单循环串行改成三线程管线：抓屏线程连续抓帧，推理线程对最新帧做检测，主线程以 250Hz 的节拍读取最新检测结果。控制循环独立于推理频率，检测间隔里持续用速度外推更新预测位置，目标转向响应在 4 毫秒内。

中间还试过 `torch.compile`，但当前环境缺 Triton，ultralytics 原生配置报 `TritonMissing`；手动替换编译模型看似快了 30%，复核发现 predictor 只在首次推理时初始化，替换后的模型根本没被调用，所谓收益只是笔记本功耗波动的噪声。结论是不做假加速，检测到 Triton 才启用，否则明确跳过并打日志。

推理尺寸也改成自适应：跟随模式用 960x608，无目标或小目标时切到 1280x800 搜索，避免方形 letterbox 浪费算力。

## 三、改善抖动与跟随手感

延迟降下来后，抖动和跟随质量成了重点。

吸附点从"顶部往下 30%"改成**底部锚点**：person 框最稳的边是底部（脚与地面的接触点），最抖的是顶部。改成从底部往上算，再用 EMA 稳住框高，框顶随姿态抖动时吸附点不再上下跳。

目标锁定的连续性也做了处理：候选锁定从"遍历顺序第一个 80 像素内"改成"80 像素内离旧锁定点最近的"，避免检测框顺序变化导致目标切换；距离跳变超过 60 像素视为重新锁定并重置速度记忆；短暂漏检有 120 毫秒的保持窗口，小目标偶发漏掉不会立刻丢目标，确认检测到大目标才释放。

近处大人物过滤很简单：框高超过屏幕 60% 直接忽略，已锁定的目标变大超过阈值也立即释放。

控制响应从"一个周期只校正约 65% 误差"改成按检测周期完成 90% 校正，另加软死区——刚离开死区时从零平滑起步，目标距中心小于死区 2.5 倍时关闭速度外推，防止抖动被前探放大。

## 四、三项硬优化：TensorRT、Kalman、ROI

这一轮在独立新版本里做了三项优化。

### TensorRT FP16 固定尺寸引擎

推理从 PyTorch 换到 TensorRT FP16。选固定尺寸是因为它对固定 shape 优化最充分，动态 shape 在切换尺寸时可能重新优化引入延迟。导出流程是 `.pt → ONNX → ModelOpt FP16 → TensorRT`。同一帧各测 12 次的对比：

```plain
PyTorch (608,960)：约 35-45ms
TensorRT 960x608 FP16：平均 6.95ms，最低 5.81ms
TensorRT 1280x800 FP16：平均 9.07ms，最低 8.11ms
```

约 5-7 倍加速，推理从管线瓶颈变成几乎不占时间。过程踩了三个坑：环境缺 ModelOpt 要先装；导出器在中文路径（`C:\Users\北天\...`）下生成的 onnx 报"文件不存在"，是 GBK 编码路径损坏，换纯 ASCII 路径解决；两次导出同名覆盖，改成自动按宽高命名。

### Kalman 滤波与跳变拒绝

实现了一个二维恒速度 Kalman 滤波器。关键在跳变拒绝：新测量相对预测的偏差（innovation）超过阈值时直接拒绝该测量、改用运动预测点，专门拦截误检或框切换造成的视角猛甩。自检里模拟 `(100,100)→(106,102)→(900,900)` 的大跳变，innovation 1126 像素被正确拒绝，输出预测点而不是跳变点。

### 锁定后的 ROI 检测

未锁定时全屏检测；锁定后以目标为中心截取屏幕 60%×70% 的 ROI 只对 ROI 推理，坐标再映射回全屏。为防止跟丢，每 5 次检测做一次全屏复查，ROI 内漏检或目标跑出就强制全屏找回。ROI 加 TensorRT 后，单帧管线 DXGI 抓屏约 4 毫秒加推理约 7 毫秒，检测率实测约 60-90fps。

## 五、实战反馈与稳定化

这三项优化合进去后实战反馈仍有问题：视角速度过快、对准目标后视野偏转到另一个方向、抖动仍明显。分析下来不是 TensorRT 的锅，而是控制增益太激进。于是保留三项优化，参数整体切换到保守稳定档：

```plain
控制响应：0.90 → 0.60
最大速度：3000 → 1600 px/s
外推上限：偏移 50% → 25%
前探：10ms → 5ms
死区：8px → 12px
新增单 tick 移动上限 12px
Kalman：测量噪声 12→20，过程噪声 900→350
```

其中最关键的是**单 tick 移动上限**——即便检测点突然跳变，一个 4 毫秒控制节拍最多移动 12 像素，从机制上杜绝"甩视角到另一边"。12 项自检全部通过，两个 TensorRT 引擎正常加载。


## 七、自检体系

整个优化靠一个闭环仿真自检撑着，共 12 项，每次改动后跑一遍，模拟两帧管线滞后加相机反馈增益：

想一想 外推是否真的生效、静止目标不绕圈、匀速目标跟随是否滞后有界、前探是否起作用、250Hz 节拍连续外推、速度记忆何时衰减、底部锚点是否抑制框顶抖动、大人物过滤小人物保留、5% 面积阈值切换、Kalman 跳变拒绝、ROI 不越界且包含目标。

有了它，改控制逻辑时能立刻知道"是不是又把绕圈引回来了"，而不是靠肉眼反复试。

## 八、几点经验

捋下来，真正有价值的不是哪个特效参数，而是几个做事方法：

1. **"声称的优化"可能是死代码**。外推写得很完整，但 delay 恒为 0，从没生效。写关键路径要验证，别相信注释。
2. **实测驱动，别猜**。抓屏注释写 20ms，实测 52ms；DXGI 的 14 倍提速来自实测而不是猜测。
3. **闭环反馈系统的稳定性是设计出来的**。没有死区的相机-检测正反馈环必然绕圈，死区加限幅加滤波才是根治。
4. **控制增益与延迟是权衡**。响应 90% 跟手但过冲，60% 稳定但略慢；单 tick 限幅是"又快又稳"的关键。
5. **TensorRT 固定尺寸**比动态尺寸更适合实时；中文路径会踩 GBK 编码坑。
6. **不要假加速**。`torch.compile` 缺 Triton 就明说不可用，绝不假装生效。
7. **多线程管线配合时间戳外推**，是把"陈旧帧"的延迟补偿掉，而不是一味提高帧率。
